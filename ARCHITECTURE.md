# Архитектура приложения «Финансы компаний»

Локальный финансовый трекер для двух компаний — **«Затон Рыбака»** и **«Арт Фокус»**.
Без сервера, без аккаунтов, без интернета: все данные лежат в JSON-файле рядом с приложением
(портативная версия) или в `%APPDATA%` (установленная версия).

---

## 1. Выбор технологического стека

**Выбран Electron + React + TypeScript + Vite, сборка через electron-builder (NSIS + Portable).**

Обоснование одним абзацем: задача требует одновременно (а) точного пиксельного воспроизведения
фирменного стиля X/Twitter — скругления, тонкие обводки, крупные жирные цифры, кастомные
ховеры, SVG-иконки, — и (б) готового установщика `.exe` плюс портативного `.exe`, собираемого
на Windows-раннере GitHub Actions за один шаг. Electron даёт браузерный движок Chromium, поэтому
весь дизайн-язык X переносится в CSS 1:1, весь UI пишется на React с типизацией, а файловая
система, диалоги сохранения и путь к данным доступны через IPC из main-процесса без нативных
модулей. `electron-builder` одной командой выдаёт `NSIS-установщик` и `portable.exe`, не требуя
Visual Studio, .NET SDK или Rust-тулчейна (Tauri/WPF упёрлись бы в необходимость Rust/Windows
для сборки, Python + CustomTkinter — в ручную стилизацию виджетов и хрупкую упаковку в exe).
Цена выбора — размер дистрибутива (~90–120 МБ), что для десктопного трекера приемлемо.

Альтернативы и почему нет:

| Вариант | Почему не выбран |
|---|---|
| Tauri + React | Меньше размер, но сборка требует Rust-тулчейна и WebView2 на целевой машине; CI дольше и капризнее. |
| WPF (.NET) | Только Windows, точная передача стиля X (градиенты, радиусы, тени, hover) — ручная работа со стилями, нет React-экосистемы. |
| Python + CustomTkinter | Стилизация ограничена, крупные цифры/скруглённые карточки/ховеры делаются вручную, упаковка в exe через PyInstaller хрупкая. |

## 2. Слои приложения

```
┌─────────────────────────────────────────────────────────────┐
│ Renderer (Chromium)                                          │
│  React 19 + TypeScript + CSS                                  │
│  Главное · Запись дня · История · Настройки                   │
│  Состояние — DataProvider (Context), расчёты — lib/calc.ts    │
└───────────────────────────▲─────────────────────────────────┘
                            │ window.finance (contextBridge, типизированный API)
┌───────────────────────────▼─────────────────────────────────┐
│ Preload (изолированный мир, sandbox: true)                    │
│  Только ipcRenderer.invoke, никакого Node API в UI            │
└───────────────────────────▲─────────────────────────────────┘
                            │ IPC (каналы data:*, app:*, window:*)
┌───────────────────────────▼─────────────────────────────────┐
│ Main (Node.js)                                               │
│  electron/main.ts   — окно, меню, диалоги, single-instance    │
│  electron/store.ts  — чтение/запись JSON, атомарно + бэкап    │
└─────────────────────────────────────────────────────────────┘
                            │
                     finance-data.json
```

Разделение ответственности:

* **main** — единственный владелец файла данных. Любая мутация сериализуется (очередь записи),
  пишется атомарно через временный файл + `rename`, перед записью делает `.backup.json`.
* **preload** — публикует узкий типизированный API (`FinanceApi` из `shared/api.ts`), никакой
  `require` в рендерер не попадает.
* **renderer** — вся логика представления и расчётов; не знает про файловую систему. В браузере
  (режим разработки/превью) тот же интерфейс реализуется адаптером на `localStorage`.

## 3. Модель данных

```ts
type CompanyId = 'zaton' | 'artfokus';   // «Затон Рыбака» | «Арт Фокус»
type ThemeMode = 'black' | 'light';      // «Чёрная» #000000 | «Белая» #FFFFFF

interface Expense {           // строка расхода внутри дня
  id: string;
  amount: number;             // ₽, >= 0
  comment: string;            // «на что и куда»
}

interface DayRecord {         // одна запись = один день одной компании
  id: string;
  company: CompanyId;
  date: string;               // YYYY-MM-DD (локальная дата)
  cashPrev: number;           // остаток наличных предыдущего дня (подставляется, редактируется)
  terminal: number;           // сумма по терминалу за день
  cashFact: number;           // фактическое наличие денег в кассе на конец дня
  reserve: number;            // сумма, отложенная в НЗ (без комиссии)
  expenses: Expense[];
  note: string;               // общий комментарий к дню (опционально)
  createdAt: string;          // ISO
  updatedAt: string;          // ISO
}

type AdjustmentTarget = 'cash' | 'terminal' | 'reserve';
type AdjustmentDirection = 'in' | 'out';

interface Adjustment {        // поступление/изъятие денег вне выручки
  id: string;
  company: CompanyId;
  date: string;
  target: AdjustmentTarget;   // куда: наличные | терминал | НЗ
  direction: AdjustmentDirection; // in — положили, out — забрали
  amount: number;
  comment: string;
  createdAt: string;
}

interface AppData {
  schemaVersion: 2;
  records: DayRecord[];
  adjustments: Adjustment[];
  settings: { theme: ThemeMode; lastCompany: CompanyId; commissionRate: number };
}
```

Файлы схемы v1 (`schemaVersion: 1`, поле `cash`) читаются без потерь: `cash` → `cashFact`,
`cashPrev` восстанавливается из предыдущей записи той же компании, `adjustments` создаётся
пустым, ставка комиссии — 2,75% (`normalizeData` в `shared/model.ts`).

Инвариант: уникальная пара **(`company`, `date`)**. Повторное сохранение того же дня и той же
компании обновляет существующую запись, а не создаёт дубль (main реализует upsert, рендерер
подхватывает запись в форму и меняет подпись кнопки на «Обновить запись»).

### Формулы показателей

Показатели считаются на лету из массива записей (`src/lib/calc.ts`), поэтому любая правка,
удаление или импорт мгновенно пересчитывают все сводки.

| Показатель | Формула |
|---|---|
| Изменение наличных | `cashFact − cashPrev` |
| Наличная выручка | `изменение наличных + Σ expenses[].amount + reserve` — из кассы ушло и то и другое |
| Выручка дня | `terminal + наличная выручка` |
| Комиссия банка | `terminal × commissionRate / 100` (по умолчанию 2,75%) |
| НЗ дня | `reserve` — без комиссии |
| **Заработано за день** | `выручка − комиссия − расходы` = `terminal − комиссия + изменение наличных + reserve` |
| Заработано за период | `Σ выручки − комиссия − расходы` |
| Наличные в кассе | `cashFact` последней записи компании ± движения по кассе и НЗ после неё |
| Движение в НЗ | `in`: `cash −amount`, `reserve +amount`; `out`: наоборот — остаток в сумме не меняется |
| Цепочка наличных | `cashChainIssues()`: `cashPrev` каждой записи = прошлый `cashFact` ± движения между днями |
| На терминале | `Σ terminal − комиссия ± пополнения/изъятия терминала` |
| Общий остаток | `наличные + на терминале + НЗ` — состояние на сейчас |
| Проверка | `общий остаток = стартовая касса + заработано за всё время ± движения` |
| Комиссия по движению | `target = 'terminal'` и `in`: `amount × commissionRate / 100` |

Расходы попадают в выручку только как восстановление наличной выручки (их уже нет в `cashFact`)
и сразу вычитаются — поэтому заработок от траты не растёт.

НЗ — не расход, а третье место хранения денег (`pots.total = cash + terminal + reserve`).
Отложенное из кассы уходит (и потому входит в наличную выручку), но из заработка не вычитается.
Иначе сумма «неприкосновенного запаса» уменьшала бы доход, хотя деньги остались у владельца.

Движения (`adjustments`) не входят ни в выручку, ни в заработок — они меняют только остатки.
Исключение: комиссия с поступлений через терминал уменьшает заработок, потому что банк реально
удержал эти деньги. Показатели считаются отдельно по каждой компании и суммарно.

НЗ — такой же кошелёк, поэтому `reserve`-движение перекладывает деньги: «положили в НЗ»
уменьшает кассу, «забрали» — увеличивает. Иначе НЗ умел бы создавать деньги из воздуха.

Цепочка остатков проверяется на лету (`cashChainIssues`): остаток «вчера» в каждой записи должен
равняться фактическому остатку прошлой записи компании плюс движения по кассе/НЗ между днями.
Разрыв показывается на Главном с датой и суммой — это признак того, что остаток вписали руками
и наличные в отчётах разъедутся.

## 4. Экраны и навигация

Левое вертикальное меню в стиле X (иконка + подпись):

1. **Главное** — герой «общий остаток» (наличные + терминал + НЗ) с полосой и легендой
   разбивки, метрики (выручка, комиссия, расходы, свободно без НЗ), карточки компаний,
   график за 14 дней, последние записи и движения.
   Переключатель периода: этот месяц / прошлый месяц / 30 дней / всё время.
2. **Запись дня** — четыре пронумерованных шага: компания и дата; деньги за день
   (терминал + НЗ, блок кассы «было вчера → стало»); расходы; комментарий.
   Внизу — липкая панель «Заработано за день» и ряд действий (сохранить, сбросить, удалить).
3. **Поступления и изъятия** — форма движения (компания, дата, цель, направление, сумма,
   комментарий, прогноз влияния), журнал с фильтрами, удаление, экспорт CSV.
4. **История** — фильтры по компании, периоду, диапазону дат и поиск; сводка по выборке;
   карточка записи со всеми девятью показателями; движения за период; экспорт в CSV.
5. **Настройки** — ставка комиссии банка, тема («Чёрная» / «Белая»), путь к файлу данных,
   резервная копия JSON, очистка данных, статистика, справка по формулам, версия.

## 5. Дизайн-система (X / Twitter)

Палитра монохромная (чёрный/белый/серый). Тем ровно две, обе заданы CSS-переменными:
`:root` — «Чёрная», `[data-theme='light']` — «Белая». Переключение меняет только атрибут
`data-theme` на `<html>` (и `color-scheme`), компоненты о цветах не знают.

| Токен | Чёрная (по умолчанию) | Белая |
|---|---|---|
| `--bg` | `#000000` | `#FFFFFF` |
| `--surface` | `#141619` | `#FFFFFF` |
| `--surface-2` | `#1C1F23` | `#F2F3F4` |
| `--border` | `#2B2F34` | `#D8DBDE` |
| `--text` | `#FFFFFF` | `#0F1419` |
| `--text-secondary` | `#8B9299` | `#536471` |
| `--accent` / `--on-accent` | `#FFFFFF` / `#000000` | `#0F1419` / `#FFFFFF` |
| `--accent-hover` | `#D7DADE` | `#2A3138` |
| `--company-zaton` | `#FFFFFF` | `#0F1419` |
| `--company-artfokus` | `#9AA1A8` | `#6B7280` |
| `--pot-cash` / `--pot-terminal` / `--pot-reserve` | `#FFFFFF` / `#9AA1A8` / `#5F666D` | `#0F1419` / `#6B7280` / `#B6BCC2` |

Миграция: сохранённое значение темы `dim` (бывший «Графит») при загрузке становится `black`,
неизвестное значение — тоже `black` (`normalizeData` в `shared/model.ts`).

Правила: шрифт `"Segoe UI", "Helvetica Neue", Helvetica, Arial, system-ui`; радиусы 16 px для
карточек и 999 px для кнопок; обводка 1 px; hover — `background: var(--tint)`;
переходы 120–160 мс; цифры — `font-variant-numeric: tabular-nums`, вес 700–800,
`letter-spacing: -0.02em`; иконки — линейные SVG 24×24 с `stroke-width: 1.75`; скроллбары тонкие.

## 7. Хранение данных и путь к файлу

1. Если задан `PORTABLE_EXECUTABLE_DIR` (запущен portable-сборка) → `<папка exe>/data/finance-data.json`.
2. Иначе → `%APPDATA%/ZatonFinance/finance-data.json` (`app.getPath('userData')`).

Перед каждой записью текущий файл копируется в `finance-data.backup.json`. Запись выполняется
в `finance-data.json.tmp` с последующим `fs.renameSync` — обрыв питания или закрытие окна в момент
сохранения не портит данные. При чтении повреждённый JSON автоматически подменяется бэкапом.

## 8. Релизный конвейер

Тег `v*` → GitHub Actions (windows-latest) → `npm ci` → `typecheck` + `vitest` →
`vite build` + `tsc` (main) → `electron-builder --win nsis portable` → шаг проверки соответствия
тега и `package.json` → GitHub Release с прикреплёнными
`ZatonFinance-Setup-<version>.exe` и `ZatonFinance-Portable-<version>.exe`, телом из CHANGELOG.
